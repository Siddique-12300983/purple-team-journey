# Week 44: Oct 26 - Nov 1, 2026

This week I ran my second AD attack, built a real SIEM, and had my best
debugging win so far. I poisoned name resolution in the lab, stood up Wazuh to
watch the whole domain, and spent a long night working out why a perfect-looking
rule would not fire. I also made the repo keep its own progress up to date so I
stop forgetting to tick things off.

## What I learned

- LLMNR and NBT-NS poisoning is simple once you see it. When DNS has no answer,
  Windows shouts the name to the whole subnet and believes whoever replies first.
  There is no check on who answers. That is the whole attack.
- A detection rule is only as good as the telemetry under it. My LLMNR Sigma rule
  was blind because the Sysmon config logged no UDP at all. The rule was fine, the
  sensor was not.
- Built-in SIEM rules can quietly swallow a real attack. A stock Wazuh rule
  dropped my Kerberoast alert to level 0 just because the request came from a real
  IP instead of loopback.
- The way to debug a missing alert is to prove the event reached the SIEM first,
  with full archiving on, and then walk the rule chain to find what catches it.
  Guessing at the rule wastes hours.
- To beat a built-in "ignore" rule, make your own rule a child of it and re-raise
  the one case you care about.
- Agents talk to the manager by IP, so they keep reporting even when DNS is broken.
  Handy, and a reminder that an attacker inside the network does not need DNS either.

## What I built or broke

- Ran LLMNR/NBT-NS/mDNS poisoning with Responder in the isolated lab, caught a
  Net-NTLMv2 hash for the domain Administrator over SMB, detected it in my own
  logs, and hardened all three protocols with GPO.
- Built a Wazuh SIEM the hands-off way: an Ubuntu cloud image plus cloud-init
  instead of clicking through the server installer. Enrolled both Windows agents
  and pulled in the Sysmon channel centrally from the manager.
- Wrote three custom Wazuh detection rules and got the full Kerberoast
  attack-and-detect loop working end to end in the SIEM.
- Made the repo README draw its own progress bars from the roadmap with a GitHub
  Action, so ticking a box is all it takes now.
- Broke and fixed: ran all four VMs at once and hit RAM and swap pressure, and
  chased a hidden stock rule that was silencing my alert.

## Commands or code worth remembering

```
# Wazuh all-in-one install (on the Ubuntu VM)
curl -sO https://packages.wazuh.com/4.14/wazuh-install.sh
sudo bash wazuh-install.sh -a

# Kerberoast test that makes a clean 4769 on the DC (run on WIN11)
klist purge
klist get MSSQLSvc/<spn>

# re-raise a service-ticket 4769 that a stock rule silenced (Wazuh local_rules.xml)
# anchor my rule as a child of the built-in "ignore" rule
<rule id="100210" level="10">
  <if_sid>92651</if_sid>
  ...
</rule>

# turn LLMNR back on or off on a client (admin PowerShell)
Set-ItemProperty "HKLM:\Software\Policies\Microsoft\Windows NT\DNSClient" -Name EnableMulticast -Value 0

# redraw the repo progress bars from the roadmap
python3 scripts/roadmap-progress.py
```

## What confused me

- Why my Kerberoast rule never fired even though the event reached Wazuh with all
  the right fields. The machine-account tickets alerted and the service-account one
  did not, and they looked identical. The answer was a stock noise-reduction rule
  dropping anything from a real IP, which my roast came from and the machine
  tickets did not.
- The Wazuh install paths moved around. The install script is served from one
  path and the Windows agent MSI from another, which cost me a bit of time.
- Four VMs at once is too much for this host. Fifteen gigs of RAM does not stretch
  to a DC, a client, a SIEM and Kali together without swapping hard.
